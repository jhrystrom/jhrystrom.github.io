# Site rebuild plan

Replace the academicpages/Jekyll stack entirely. Keep the content, throw out everything else.
Target: a static site generated by one readable Python file, published by a short GitHub
Actions workflow, with `just check` failing locally on anything malformed.

> Add `NOTE:` lines anywhere below. I'll read them before implementing.

---

## 1. The one real decision

**Recommendation: no framework. A ~200-line `build.py` run by `uv`.**

Why not the obvious candidates:

- **Jekyll (current)** — the local toolchain is already broken: `ruby` here is macOS system
  2.6.10, `.ruby-version` asks for 3.2.11, and `bundle` errors out on a missing bundler
  4.0.20. Fixing that means rbenv/mise + a Gemfile.lock to babysit, for a generator we'd be
  fighting anyway.
- **Hugo** — one binary, genuinely good, but it *is* a framework: template lookup order,
  archetypes, taxonomies, shortcodes, and a config surface that shifts between releases
  (the layout lookup rules changed materially in 2025). For 4 posts that's more convention
  to learn than code to write.
- **Astro / Eleventy** — `node_modules`, a lockfile, and a yearly major upgrade on a site
  you touch a handful of times a year. Rules itself out on "not too framework heavy".

What tips it: **the validation you asked for is cross-file.** The check that matters most —
"this `translation_key` group has exactly one `original: true`, and no two members share a
`lang`" — is not expressible in Hugo's config, and not in Astro's Zod content schemas either
(those validate one file at a time). Every option needs a custom validator script. Once
you're writing that script, having it also do the rendering costs ~80 extra lines and
removes a whole toolchain. The build *is* the checker.

You read Python daily; you will not read Go templates daily.

## 2. Dependencies, total

| Tool | Install | Already present? |
|---|---|---|
| `uv` | — | ✅ 0.12.8 |
| `just` | — | ✅ 1.53.0 |

That's the whole list. No Ruby, no Node, no Homebrew packages, no `node_modules`.

`build.py` declares its own dependencies inline (PEP 723), so there is no `pyproject.toml`
and no virtualenv to manage:

```python
# /// script
# requires-python = ">=3.12"
# dependencies = ["markdown~=3.7", "jinja2~=3.1", "pyyaml~=6.0"]
# ///
```

`uv run build.py` resolves and caches them on first run. `uv lock --script build.py` pins
them into `build.py.lock` so CI and your laptop build identically.

Every check tool runs through `uvx`, which needs no prior installation:
`ruff`, `mdformat`, `codespell`.

## 4. Content model

One post = one markdown file. Minimum viable front matter is two lines:

```yaml
---
title: "Research projects are IT projects — and IT projects are delayed"
date: 2025-01-07
---
```

A translated pair adds three keys to **both** files:

```yaml
lang: da                            # da | en
translation_key: agents-are-here    # shared by every version
original: true                      # exactly one per key is true
```

Optional: `permalink:` (to pin a URL), `venue:` (talk notes), `draft: true`.

**Unknown keys are a build error.** `titel:`, `data:`, `orginal:` fail the build with the
file and key named, rather than silently vanishing from the site. That is the single most
useful check here and it's why the allowed-key list lives in `build.py`.

### URLs

Default `/posts/<year>/<month>/<slug>/`, derived from the filename. All four existing pages
already carry explicit `permalink:` values, and `build.py` honours the field verbatim, so
every current URL survives with zero redirect machinery:

- `/posts/2025/01/research-it-project/`
- `/posts/2026/09/agents-are-here-dan/`
- `/posts/2026/09/agents-are-here-eng/`
- `/talks/2024-michaelmas-dphil-poster/`

Not preserved: `/publications/*`, `/teaching/*`, `/blog-posts/`, `/cv/`. See §5.

Filenames keep the `-dan`/`-eng` suffixes. I proposed normalising them to `-da`/`-en` last
round; that was taste, it breaks two live URLs, and `lang:` already carries the ISO code
that `<html lang>` and `hreflang` actually use. Dropped.

NOTE: We should consider better posting ergonomics. The current setup has a lot of duplication, so the _file names_ could be simplified but the URLs shouldn't be broken. However, this is for the future.

## 6. Translations

Selection rule, one line in the template context: a post is listed on the front page and in
the feed unless it says `original: false`. A post with no language keys at all is listed —
so monolingual posts need no ceremony.

On the front page, a post whose `translation_key` has a sibling gets
`(English available)` / `(Dansk tilgængelig)` linking to it. On the post page itself, a grey
one-liner under the date:

- on the Danish original: *Also available in English (AI-translated).*
- on the English version: *This is an AI translation of the Danish original.*

`build.py` emits `<link rel="alternate" hreflang="da|en">` pairs on both, a self-referential
`<link rel="canonical">` on each, and `<html lang>` from `lang:`. Both versions go in
`sitemap.xml`; only the original goes in `feed.xml`.

## 7. `just check` — the part you care about

```
just          # list commands
just dev      # build + serve on :8000 + rebuild on change
just build    # write _site/
just fmt      # format everything in place
just check    # read-only; non-zero exit on any problem
```

`just check` runs, in order, stopping at the first failure:

```make
check:
    uv run build.py --out /tmp/_check --strict     # 1
    uvx ruff format --check .                      # 2
    uvx ruff check .                               # 3
    uvx mdformat --check content/                  # 4
    uvx codespell --skip="*-dan.md" content/       # 5
```

**1. `build.py --strict`** — the real check. Fails on:

- front matter that isn't valid YAML, or is missing `title` / `date`
- **any front-matter key not in the allowed set** (catches `titel:`, `orginal:`)
- `lang` outside `{da, en}`; `date` not a real date
- a `translation_key` group with zero or two `original: true` members
- a `translation_key` group with two files claiming the same `lang`
- two pages resolving to the same output URL
- a `permalink` that isn't lowercase, slash-delimited, and trailing-slashed
- **an internal link or image that doesn't resolve** — `[x](/posts/…)` pointing at a page
  that isn't generated, or `![](/images/…)` with no such file. This is the check that would
  have caught the template's dangling links.
- an unused file in `static/images/` (warning; `--strict` promotes it to an error)

Failures print as `content/posts/foo.md:4: unknown front-matter key 'titel'`, so the
editor's problem-matcher can jump to them.

**2–3. `ruff`** — formats and lints `build.py` itself. One binary, zero config.

**4. `mdformat --check`** — normalises the markdown: consistent list markers, reference-style
link spacing, no trailing whitespace, hard-wrap left alone. Fails on any file it would
change; `just fmt` rewrites them.

**5. `codespell`** — English typos. Skipped on `*-dan.md`, since a Danish corpus makes it
useless. Marked optional; say the word and I'll drop it.

Deliberately **not** in `just check`: external link checking. Your posts link out heavily
(the Danish one has ~10 external links, several to paywalled news sites) and those URLs will
break, rate-limit, and 403 for reasons unrelated to your commit. Blocking a publish on that
is how a check suite gets ignored. Instead:

```
just check-links   # on demand, and a weekly scheduled CI job that opens an issue
```

## 8. GitHub Actions

Two jobs. `check` runs on every push and PR; `deploy` runs only on `master` and only after
`check` passes — so a formatting failure can't reach the live site.

```yaml
name: Site
on:
  push:
    branches: [master]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: astral-sh/setup-uv@v6
        with:
          enable-cache: true
      - run: uvx --from rust-just just check

  deploy:
    needs: check
    if: github.ref == 'refs/heads/master'
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v5
      - uses: astral-sh/setup-uv@v6
        with:
          enable-cache: true
      - run: uv run build.py --out _site
      - uses: actions/upload-pages-artifact@v3
        with:
          path: _site
      - id: deployment
        uses: actions/deploy-pages@v4
```

CI runs **the same `just check` you run locally** — no duplicated command list, so the two
cannot drift.

Things I will verify rather than assume, before this lands:

- exact current major versions of `actions/checkout`, `astral-sh/setup-uv`,
  `upload-pages-artifact`, `deploy-pages` — and pin each to a commit SHA
- that `uvx --from rust-just just` actually resolves on the runner; fallback is
  `extractions/setup-just`, or inlining the five check commands
- I'll push the branch and watch a real run go green before merging to `master`

**Manual step you have to do:** repo Settings → Pages → Source, change from *Deploy from a
branch* to *GitHub Actions*. Until you flip that, the workflow will build and the deploy step
will fail. I can't do it from here.

## 9. Visual design

Single column, `max-width: 36rem`, centred. System font stack — no webfont request at all.
Body 18px/1.65. Near-black on off-white, plain underlined links, grey for dates and the
translation note. `prefers-color-scheme: dark` flips the two colour tokens. Header is your
name linking to `/`; footer is one line of links. No sidebar, no author card, no share
buttons, no comments, no analytics, no JavaScript on any page.

~150 lines of hand-written CSS, no preprocessor, served as one file.

## 10. Order of work

1. Branch `rebuild`.
2. `build.py` + templates + CSS, building against the content in place.
3. Migrate the 4 content files + 3 static assets into the new tree; write `index.md`.
4. `justfile`; get `just check` green.
5. Workflow; push branch; confirm the `check` job passes in CI.
6. Delete the old tree (§3). `just check` again.
7. You flip the Pages source setting.
8. Merge to `master`; confirm the live site, and spot-check the four preserved URLs.

Old files stay in git history throughout, so step 6 is recoverable with `git revert`.
